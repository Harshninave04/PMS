# Medistra PMS Code Audit

**Audit date:** 2026-10-30  
**Scope:** Static review of `src/app`, `src/components`, `src/controllers`, `src/services`, `src/models`, `src/lib/rbac`, `tests`, `scripts`, and the repository Docker/environment configuration.  
**Constraint:** Audit only. No application code was changed and no commit was created. This report is the only requested deliverable.

## Evidence and limits

- **Verified in code** means the behavior or absence is supported by the checked-in source/configuration paths cited below.
- **Not verified at runtime** means I did not validate a deployed hospital environment, live MongoDB data, external storage bucket policy, network exposure, or real user journey in a browser. “Missing” means no implementation was found in the repository surfaces inspected; it does not rule out an external integration.
- I inspected the route/page inventories and searched the requested surfaces for TODO/FIXME/stub language, auth checks, navigation destinations, and domain implementations, then traced the core flows through route/controller/service/model code. This is a static code audit, not a literal line-by-line transcription of every UI component.
- `.env` exists locally and is git-ignored; its values are intentionally not reproduced here. Production Compose defaults and hard-coded seed fallbacks are discussed below.
- **Validation run:** `npm test` passed (the configured RBAC tests); `npm run typecheck` passed. `npm run lint` failed with **570 errors and 308 warnings** across the existing source tree (examples include `no-explicit-any`, unused variables, hook-dependency warnings, and image-element warnings). No application code was changed, so these are baseline findings, not regressions from this audit. No live database, end-to-end browser, production build, or backup-restore test was run.
- **Severity convention:** High = serious privacy/security, money, or patient-care risk; Med = material reliability or workflow risk; Low = limited scope, cleanup, or usability issue.

## 2. PENDING / INCOMPLETE FLOWS

| Flow | Verified path through code / break or omission | Severity | Suggested fix |
|---|---|---:|---|
| **OPD: register → book → check-in → consult → pharmacy → bill** | Patient registration and appointment creation exist (`patient.controller.ts`, `appointment.controller.ts`). The queue supports check-in/call/start actions; consultation completion creates a `ClinicalRecord` and optional prescription (`src/app/api/appointments/queue/route.ts`, `src/app/api/appointments/[id]/complete-consultation/route.ts`). Prescription dispensing exists (`src/app/api/pharmacy/prescriptions/`, `src/app/api/pharmacy/dispense/`). **The chain is not one billing workflow:** pharmacy creates a separate dispense/bill record; it is not automatically reconciled to the central invoice/payment ledger. Appointment-to-doctor schedule availability is not checked by the appointment creation service. | Med | Define and persist the OPD charge lifecycle; link consult, prescription, dispense, invoice, payment, and cancellation/refund; enforce the doctor’s active schedule/slot capacity at booking. |
| **IPD: admit → care team → treatment → discharge request → nurse → billing → discharge → packet** | This is the most complete workflow. Admission claims an available bed; care-team assignment is supported; nursing has assigned-patient rosters, medication administration, daily records and supplies. Doctor discharge request, nurse billing handoff, invoice/billing queue, discharge gates, and discharge packet exist across `src/services/admission.service.ts`, `src/controllers/admission.controller.ts`, `src/controllers/nursing.controller.ts`, `src/services/nursing.service.ts`, `src/services/billing-flow.service.ts`, and `src/services/discharge-packet.service.ts`. Nurse discharge additionally requires assigned active admission and finalized daily records for each hospital day. Packet is rendered for browser **Print / Save as PDF**, not generated as a server-signed/stored PDF. | Med | Preserve the existing gates; add end-to-end tests for assigned/unassigned nurse, incomplete daily records, billing, and bed release. Decide whether signed/versioned PDF storage is required for the hospital’s legal workflow. |
| **Pharmacy stock and dispensing** | Medicine catalogue, stock adjustment, expiry analysis, prescription dispensing, and dispense records exist (`src/services/pharmacy.service.ts`; pharmacy API/pages). Dispense decrements stock item-by-item before saving the dispense; it does not use a Mongo transaction or a conditional “stock >= quantity” update. A later write failure can leave stock changed without a dispense record; concurrent dispensing can take stock below zero. Direct adjustment clamps negative results to zero rather than reporting rejected quantity. | High | Atomically reserve/decrement with a nonnegative-stock predicate, persist the dispense in the same transaction where available, and fail/compensate explicitly on partial failure. |
| **Billing, payments, refunds** | Invoice and payment APIs/services exist; payments validate positive amount/balance, refunds are invoice-bound and capped against paid amount, and advances are recorded against admissions (`src/services/payment.service.ts`, `src/services/invoice.service.ts`, finance API/pages). Receipt + invoice writes use a transaction only when MongoDB topology supports it. The shipped Compose database is a single `mongo:7.0` instance without replica-set configuration, so the service’s non-transaction fallback is used there. | High | Run a replica set/transaction-capable MongoDB in deployed environments or redesign with durable idempotent ledger/reconciliation. Add failure-injection tests for payment, refund and receipt grouping. |
| **Lab / radiology orders and results** | No lab/radiology order, result-entry, or report model/service/API was found. Patient document categories include `LAB_REPORT` and `RADIOLOGY`, which represent attachments only, not a diagnostic workflow. | High | Add order lifecycle (order, sample/imaging status, result entry, clinician review, amendments, report output) with patient/admission/branch authorization and audit history. |
| **Bed / ward management** | Ward, room and bed CRUD/availability pages and APIs exist. Initial admission bed claim is atomic (`status: AVAILABLE` predicate), but transfer frees the old bed and marks the requested new bed occupied without checking that the new bed is available or updating both beds and admission atomically (`src/services/admission.service.ts`). | High | Require `AVAILABLE` on the target bed; use a transaction or guarded multi-step state transition with reliable compensation and concurrency tests. |
| **Appointment cancellation / rescheduling** | UI and APIs are wired (`appointments/list/page.tsx`, `/api/appointments/cancel`, `/api/appointments/reschedule`). Doctor ownership is checked, but non-doctor flows do not enforce branch scope on the appointment. Rescheduling does not consult the schedule model or reject invalid dates before constructing the update. | High | Add branch-scoped resource lookup and conditional updates, validate dates/time zones, and verify target doctor availability and status transitions. |
| **Users and roles** | Admin user/role screens and APIs exist; role permissions are managed and RBAC tests cover role rules. Authentication accepts legacy plaintext passwords as well as bcrypt hashes (`src/lib/auth.ts`). | Med | Migrate plaintext records to bcrypt and remove plaintext comparison; add tests for account lifecycle, role-change propagation, and branch-scoped administration. |

## 3. SECURITY AND DATA SAFETY

| Item | Where in code | Severity | Suggested fix |
|---|---|---:|---|
| **Patient files are configured as public objects.** Storage creates Supabase buckets with `public: true`, and S3 uploads request `ACL: "public-read"`. The upload API stores patient documents and returns their URLs. A permission on upload does not make the resulting object private; anyone holding/discovering the URL may be able to read it. | `src/lib/storage.ts`; `src/app/api/upload/route.ts`; `src/controllers/patient.controller.ts` | High | Use a private bucket, short-lived signed read URLs, strict object access policy, and a migration/review of already-uploaded documents and public ACLs. Treat this as a PHI exposure risk until the external bucket policy is verified. |
| **Branch scope is not applied on several live OPD endpoints.** The appointment list controller has branch logic, but the plural queue/cancel/reschedule handlers query/update by date or ID and only add doctor ownership restrictions. `complete-consultation` also loads an appointment without checking its branch for non-doctor actors. The queue response populates patient name/contact/UHID. The actual UI calls these endpoints. | `src/app/api/appointments/queue/route.ts`; `src/app/api/appointments/cancel/route.ts`; `src/app/api/appointments/reschedule/route.ts`; `src/app/api/appointments/[id]/complete-consultation/route.ts`; contrast `src/controllers/appointment.controller.ts` | High | Resolve the target record using the RBAC scope/branch filter before read or mutation; enforce the branch again in conditional updates. Add cross-branch tests for list, read, check-in, cancel, reschedule, and consultation completion. |
| **Upload API does not authorize the supplied patient against branch scope.** It checks `patients.documents:upload` but bypasses `PatientController` and calls the service with a client-supplied patient ID. It also trusts client-supplied file MIME type and has no explicit size/type allow-list before reading the whole file into memory. | `src/app/api/upload/route.ts`; `src/lib/storage.ts`; compare `src/controllers/patient.controller.ts` | High | Resolve and authorize the patient server-side with `authorizeRequest(..., "Patient")`, validate ObjectId and patient scope, constrain file size/extensions/content by inspection, and avoid buffering unbounded bodies. |
| **Production credentials/secrets are committed as Compose defaults.** Compose sets a fixed `NEXTAUTH_SECRET`, a predictable default admin password, and a basic-auth password for mongo-express. `src/seed.ts` also has a `password123` fallback. These are configuration defaults, not values copied from the local `.env`. | `docker-compose.yml`; `src/seed.ts`; `src/lib/auth.ts` | High | Require secrets from protected deployment configuration; reject known/default secrets at startup; rotate any deployment that used these values; remove or guard insecure seed defaults. |
| **MongoDB admin UI is exposed with fixed credentials.** Compose publishes mongo-express on host port 8081 with a hard-coded basic-auth username/password. Mongo itself is not host-published, which is a positive control, but mongo-express is reachable through the host mapping. | `docker-compose.yml` | High | Disable mongo-express in production profiles; otherwise bind to localhost/private management network and require externally supplied credentials plus TLS/VPN controls. |
| **Legacy plaintext password authentication and no login throttling.** Credential verification explicitly compares the submitted password to stored plaintext for non-bcrypt hashes. No rate-limit, lockout, or throttling implementation was found. | `src/lib/auth.ts`; `src/app/api/auth/[...nextauth]/route.ts` | Med | Use a migration path that hashes legacy passwords on successful login or forces reset, then reject plaintext storage; add IP/account throttling and alerting. |
| **Page permission check can be skipped on identity-resolution errors.** Dashboard layout catches `resolveRequestIdentity()` failures and sets identity to null; in that branch it loads the session and does not call `canOpenPage`. API handlers still have separate checks, but the page boundary is not consistently fail-closed. | `src/app/(dashboard)/layout.tsx`; `src/lib/rbac/guard.ts` | Med | Return/throw a 401/403/503 when identity resolution fails; only use the JWT snapshot for presentation, never as a bypass around page authorization. |
| **Clinical audit trail is incomplete.** The code includes role audit records (`src/lib/rbac/audit.ts`, `src/models/role-audit.model.ts`) but I found no general append-only audit log for patient reads/exports, clinical record changes, medicine administration, billing/refunds, or discharge, and no audit-trail screen. | `src/lib/rbac/audit.ts`; `src/models/role-audit.model.ts`; admin pages | Med | Add append-only actor/action/resource/branch/time audit events for sensitive clinical and financial operations; restrict and retain them according to policy. |
| **No API rate limiting was found.** This includes login and high-cost list/upload/report endpoints. | `src/app/api/`; `src/lib/auth.ts`; dependencies/config | Med | Add shared server-side throttling and request-size limits at both application and edge/proxy layers. |

## 4. DATA QUALITY AND RELIABILITY

| Item | Where in code | Severity | Suggested fix |
|---|---|---:|---|
| **Multi-record bed transitions are not atomic.** Admission creation compensates if admission persistence fails, but a process crash can strand a claimed bed. Transfer releases the prior bed before taking the new one and does not verify availability; discharge updates admission then releases the bed with manual compensation. | `src/services/admission.service.ts` | High | Use transaction-capable MongoDB or guarded transition/outbox reconciliation; add invariant checks and recovery for orphaned occupied beds. |
| **Pharmacy stock writes can diverge from dispense records.** Stock is decremented before the dispense document is created, with no conditional nonnegative predicate or rollback. Direct stock adjustment silently clamps at zero. | `src/services/pharmacy.service.ts` | High | Add atomic stock constraints, transaction/reconciliation, and explicit stock-adjustment validation with audit trail. |
| **Payment atomicity depends on topology.** Payment service conditionally starts a transaction; the supplied single-node Compose MongoDB does not configure a replica set. In that topology receipt and invoice writes can partially complete if a later operation fails. | `src/services/payment.service.ts`; `docker-compose.yml`; `src/lib/mongo-transaction-support.ts` | High | Make transaction-capable MongoDB a deployment prerequisite or implement an idempotent ledger and reconciliation process. |
| **OPD date windows use server-local time, not the hospital timezone helper.** Appointment service and queue endpoints use `setHours(0,0,0,0)` and `new Date()` for day grouping; container timezone may differ from the hospital timezone. Nursing/medication code has a dedicated hospital-time helper, but the appointment paths do not use it. | `src/services/appointment.service.ts`; `src/app/api/appointments/queue/route.ts`; `src/lib/hospital-time.ts` | Med | Use a configured hospital timezone for appointment day boundaries, token generation, queue membership, and display; test around midnight and DST transitions. |
| **Request validation is uneven.** Some core controllers validate IDs, required fields and lengths, but appointment service accepts `any`; direct appointment handlers construct dates and issue updates with inconsistent ID/date validation. Upload accepts a whole body/file without a bounded size or content allow-list. | `src/services/appointment.service.ts`; `src/app/api/appointments/`; `src/app/api/upload/route.ts`; `src/dto/` | Med | Use typed DTO/schema validation at every API boundary; validate ObjectIds, enum transitions, date ranges, money precision, and allowed update fields. |
| **Upload/storage failures can be success-shaped.** A patient-link error is swallowed and the fallback storage provider returns a URL without writing an object. | `src/app/api/upload/route.ts`; `src/lib/storage.ts` | Med | Surface provider failures; distinguish uploaded, linked, and persisted outcomes, and clean up partial writes. |
| **Indexes are present but not a full migration strategy.** Several high-volume paths have indexes (e.g. active/assigned admissions, daily nursing records, vitals, care tasks, receipts). Operational index scripts exist, but there is no general migration runner/version ledger or rollout process visible. | `src/models/*.model.ts`; `scripts/` | Med | Maintain versioned, idempotent schema/index migrations with deployment ordering and rollback/verification plans. |
| **Seed command is destructive.** The seed script deletes all users, roles, menus, organizations, departments, designations, doctors, staff and medicine catalogue before reseeding. It has no production-environment guard. | `src/seed.ts`; `package.json` (`seed` script) | High | Retire this as a routine production command; require explicit destructive confirmation/environment guard and use non-destructive bootstrap/migrations for production. |
| **No backup/restore procedure is supplied.** Compose volumes persist MongoDB and uploads, but persistence is not backup; no backup, restore, retention, or recovery test script was found. | `docker-compose.yml`; `scripts/` | High | Add encrypted automated backups, off-host retention, documented RPO/RTO, and regular restore drills. |
| **Error handling/logging is inconsistent.** Many controllers log to console; upload linking errors are swallowed; several handlers return raw exception messages. There is no centralized structured logger/trace or monitoring integration visible. | `src/controllers/`; `src/app/api/upload/route.ts`; `src/instrumentation.ts` | Med | Use structured, redacted server logs with correlation IDs; return stable public errors while retaining diagnostic details server-side. Never log clinical payloads or credentials. |

## 7. QUICK WINS VS BIG FEATURES

Estimates below are implementation targets, not measured commitments; they assume an engineer familiar with the current code and no external procurement delays.

### Top 10 quick wins (each targeted under one day)

| # | Quick win | Why |
|---:|---|---|
| 1 | Remove committed Compose secret/password defaults; validate required secrets and rotate any deployed defaults. | Immediate account/session compromise reduction. |
| 2 | Disable mongo-express in production Compose or bind it to a private management interface with supplied credentials. | Closes an exposed database administration surface. |
| 3 | Add branch-scoped appointment reads and conditional writes to queue, cancel, reschedule, and consultation completion; add focused cross-branch tests. | Fixes a confirmed multi-branch PII/action boundary gap. |
| 4 | Make upload authorization patient-scoped and return failure if patient-document linking fails. | Prevents cross-branch attachment and false success. |
| 5 | Enforce an upload size limit and explicit accepted file formats; reject MIME/extension mismatches. | Reduces memory/DoS and unsafe-document risk. |
| 6 | Remove the fake successful storage fallback from production and return an explicit service-unavailable error when no provider is configured. | Stops broken document links being presented as valid uploads. |
| 7 | Reject plaintext password comparison and supply a one-time migration/reset path for legacy accounts. | Closes continued acceptance of plaintext credential records. |
| 8 | Use hospital-timezone day boundaries in OPD queue and token generation. | Reduces wrong-day queue/token behavior around midnight. |
| 9 | Make pharmacy stock decrement conditional on sufficient stock and refuse negative/oversized adjustments. | Prevents oversell and simple stock inconsistency. |
| 10 | Add fail-closed handling to dashboard identity resolution and expose a health check for the app. | Makes permission failure behavior predictable and improves operations. |

### Top 10 bigger features ranked by value for a real hospital

| Rank | Feature | Hospital value |
|---:|---|---|
| 1 | Private patient-document storage, branch/patient authorization, and auditable access. | Core confidentiality and regulatory/safety control for PHI. |

## 8. RECOMMENDED ROADMAP

| Week | Recommended order of work | Exit criteria |
|---|---|---|
| **Week 1 — Contain privacy/security risks** | Rotate/remove Compose secrets and default credentials; disable or secure mongo-express; make document storage private; authorize upload patient/branch scope; fix branch checks for all plural OPD endpoints; fail closed on page identity errors; add focused regression tests. | No public PHI bucket/object ACL; branch A cannot list/read/mutate branch B appointments; upload to unauthorized patient fails; no production defaults accepted. |
| **Week 2 — Protect operational data integrity** | Decide/enable transaction-capable MongoDB; make stock/dispense and bed transitions atomic or explicitly recoverable; enforce stock nonnegative invariants; validate and constrain appointment dates and IDs; centralize hospital-timezone queue boundaries; add failure-injection/concurrency tests. | Failed payment/dispense/transfer leaves no partial state; concurrent booking/dispensing tests preserve invariants; time-boundary tests pass. |
| **Week 3 — Establish operations and auditability** | Add versioned migration procedure; implement automated backup/retention and restore drill; add health/readiness endpoints and structured redacted logs; create append-only clinical/financial audit events; add CI jobs for typecheck/lint/tests/build and service/API suites. | CI gates changes; a documented restore is exercised; sensitive write actions include actor/time/resource audit entries. |
| **Week 4 — Close a high-value clinical workflow gap** | Select lab/radiology or revenue-cycle integration as the first vertical slice; define clinical ownership and result review; design permission/branch scope, audit, amendments, and export before UI; pilot with representative users and test data. | One complete order-to-result-to-review (or charge-to-payment-to-reconciliation) flow works end-to-end with RBAC, branch isolation, audit, and recovery tests. |

**Overall recommendation:** Do not treat the current application as production-ready for real patient data until public document access, OPD branch scoping, hard-coded deployment credentials, transaction topology, and backup/restore are addressed and verified in the target environment.
